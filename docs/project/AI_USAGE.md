# How AI tools were used

This is an individual project. One developer worked alone, with AI tools as the only help.

**Tool:** Claude Code (an AI coding agent running in the terminal, model Claude Sonnet 5.5), driven by one structured "master prompt" (`PROMPT.md`) written beforehand and refined by the developer through chat.

## Process
1. The developer wrote `PROMPT.md` (requirements, staged checkpoints, quality bars) and pasted the official assignment text.
2. The agent built the backend first (state machine, validation, documents, seed data) with tests, then the React client, then the audit log, then security hardening, tests and docs, reporting after each stage.
3. The developer reviewed behaviour by running the app and gave direction in chat.

## Developer decisions that changed the build
- Plain JavaScript instead of the TypeScript the prompt preferred.
- Emergency leave: over-3-day leave may be filed without documents, which become owed. One outstanding emergency leave allows one more emergency leave only; two outstanding block everything.
- One-click demo accounts, the demo password hidden from the UI, MongoDB Atlas via `.env`.
- Past start dates blocked (the agent first widened the past window after a misunderstanding; the developer corrected it).

## Example prompts
- "Go through prompt.md, build it. MERN stack. First build what the pasted text asks for…"
- "In case of emergency leave, provide the option that despite being over 3 days, emergency leave can be submitted but supporting documents must be furnished…"
- "User shouldn't be able to select past dates when applying for a leave."

## What was generated vs reviewed
All code was generated by the agent. It was verified by automated tests (unit, API integration, security, component tests) run after each change, and by a manual click-through in a real browser against MongoDB Atlas. The developer set the rules and checked behaviour; line-by-line review of every file is not claimed.

## Mistakes the AI made and how they were fixed
- Wrote tests with inputs the validators correctly rejected (a 4-character reason, a date over a year ahead); found because tests failed, and the tests were corrected, not the rules.
- Wrongly expected HTTP 409 where the design (correctly) gives 403 for "right state, wrong person".
- Shell quoting slips: backticks in a shell string removed a message from `shared/src/index.js`, and a `$'` in a JavaScript `replace` corrupted `security.js`. Both were noticed from syntax errors and rewritten.
- A rate limiter shared across app instances made a test fail; it is now created per app.
- Documented the shared demo password and later removed it from user-facing places on request.
- First misread "select past dates" (the opposite of the intent); reversed after clarification.
- Initially left a claim in the README that the UI was untested; replaced after real browser testing.

## Not done by AI judgement
Choosing which requirements to prioritise, the emergency-leave policy, and acceptance of the final behaviour were the developer's.
